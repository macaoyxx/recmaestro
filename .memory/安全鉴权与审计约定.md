# 安全鉴权与审计约定（内部接口 token / 登录锁定 / 限流 / 审计）

## 是什么 / 规则

### worker 内部接口共享密钥（INTERNAL_API_TOKEN）
- 环境变量 `INTERNAL_API_TOKEN`，scheduler 与 worker **必须一致**；两角色启动强校验，缺省直接报错退出（fail fast，同 `JWT_SECRET` 惯例）
- 请求头 `X-Internal-Token`；常量在 config 包：`config.InternalTokenHeader`——放 config 是为了让双方共用而不引入 scheduler→worker 的反向依赖
- worker 中间件 **fail closed**：token 未配置时拒绝全部内部请求（`crypto/subtle.ConstantTimeCompare` 常数时间比较防时序侧信道）
- scheduler 侧有**两条**携带路径，新增转发场景两条都要带：`forwardToWorker`（JSON 转发）与 `proxyToWorkerInternal`（下载反代）
- `/healthz`、`/metrics` 在 main.go 单独挂载、不在 InternalRouter 上，不受 token 保护——有意为之

### 用户处置护栏（V0.1.0 后补）
- 内置管理员（`store.BuiltinAdminUsername` = "admin"，seedAdmin 创建）**不可删除、不可禁用**——系统的永久管理入口；其余管理员（含用户自建）均可正常删除/禁用
- 当前登录账号**不可删除、不可禁用**（防止把自己锁在门外）
- 前端用户页对受保护行**直接隐藏**禁用/删除按钮（判定：username==='admin' 或等于当前登录用户名；登录时 username 落 localStorage，/api/me 兜底），后端仍是权威拦截
- "最后一个启用管理员"计数护栏保留作兜底——内置 admin 永远在，正常路径永不触发

### 登录锁定与解锁
- 锁定 = `status=disabled` + `failed_login_count≥5` **两条件叠加**；只改状态不清计数 = 账号永久锁死（V0.1.0 前的真实 bug）
- 解锁入口恰两处，都调 `store.Unlock`（只清计数，不动 last_login_at）：admin 置 enabled（`PATCH /users/:id/status`）、重置密码（`PATCH /users/:id/password`）

### 登录 IP 限流
- 每 IP 每分钟 10 次（固定窗口、内存计数、**单机语义**，多副本部署各副本独立计数），超限 429 + Retry-After
- 限流器随 `Router()` 创建：**每个 Router 实例独立计数**——测试里多次 `Router()` 互不影响，但单个测试函数内的登录调用别超 10 次否则误触 429

### 审计日志写入点（V0.1.0 后补：名称快照 + 通用三元组）
- 动作常量统一登记在 `store/audit_log.go`（`AuditLoginSuccess` 等 12 个），**新增动作必须在此登记**，不要散落字符串
- 资源类型枚举：`AuditResourceUser` / `AuditResourceTask`（前端 `AuditLog.vue` 的 resourceText 映射展示名，新增类型两端登记）
- **对象通用三元组**：`resource(类型) + resource_id + resource_name`——resource_name 是唯一通用名称列（用户→用户名、任务→任务名），**新增资源类型复用此列零加列**；操作者另有一对 `user_id + operator_name`
- **名称写入时快照落库**（迁移 000002）：资源日后删除审计仍能读出名称；不搞读取时关联
- 写入走 `s.audit(c, auditEvent{...})`（scheduler/handler_audit.go）：事件结构体带 OperatorID/OperatorName/ResourceName；中止任务、用户启停/重置密码等 handler 会先加载目标实体拿名称（顺带把不存在的 id 拦成 404）
- 写入点清单：登录成功/密码错误/锁定；创建用户/启停/重置密码；任务编辑/中止/删除；手动合并/删除文件
- **刻意不审计**：常规任务创建/取消/重试——量大且非敏感，任务日志（live_rec_task_logs）已有全生命周期记录
- `s.audit()` 同步落库，失败仅 `[warn]` 日志、不阻断业务响应
- 查询：`POST /api/audit-logs/list`（admin，分页入参内嵌 `api.PageQuery`）
- 迁移踩坑：MySQL 8 里 `CAST(id AS CHAR)` 产生 utf8mb4_0900_ai_ci，与表的 utf8mb4_unicode_ci 列比较报 Illegal mix of collations——JOIN 条件里 CAST 后必须显式 `COLLATE utf8mb4_unicode_ci`（000002 已踩）

## 关键文件
- `internal/config/config.go` —— `InternalAPIToken` 字段、`InternalTokenHeader` 常量、env 覆盖
- `internal/worker/internal_api.go` —— `internalAuth()` 中间件（fail closed）
- `internal/scheduler/handler_file.go` —— `forwardToWorker` / `proxyToWorkerInternal` 两条携带路径
- `internal/scheduler/handler_audit.go` —— `audit()` 助手 + 查询接口
- `internal/store/user.go` —— `Unlock()`
- `internal/scheduler/login_ratelimit.go` —— 限流中间件
- `deploy/.env.example`、`deploy/docker-compose.yml` —— 部署注入

## 为什么这么做（设计权衡 / 踩坑）
- fail closed 而非 fail open：内部接口能合并/删除/下载文件，token 缺失时放行等于裸奔，宁可启动报错把问题暴露在部署时
- 解锁不清 `last_login_at`：重置密码/启用不是一次成功登录，两个语义分开（登录成功才走 `ResetFailedLogin`）
- 审计失败不阻断：审计是观测不是关键路径，写库抖动不该让管理员操作返回 500
