# 后台循环与优雅停机

## 是什么 / 规则

- 两角色均处理 SIGTERM/SIGINT 优雅停机（V0.1.0 起 scheduler 补齐，与 worker 对齐）：
  - **scheduler**：`signal.NotifyContext` 的 ctx 传给**所有**后台启动器（`Logger().Start` / `RebuildQueues` / `RegisterService` / `RunDispatcher` / `RunMetricsCollector` / `RunLogCleanup`）→ 收信号后 `http.Server.Shutdown`（5s 等在途请求）→ 各循环随 ctx 退出 → sleep 1s 等日志缓冲 flush
  - **worker**：等在录任务收尾最长 8s（docker stop 默认 10s 宽限内尽力，超时强杀由宕机恢复机制接管）
- `TaskLogger.flushLoop` 在 `ctx.Done` 时 flush 剩余缓冲再退出——这是所有日志产生方必须拿到**可取消 ctx** 的原因
- **新增任何后台循环的铁律：必须接收并监听 ctx**（`select { case <-ctx.Done(): return; case <-ticker.C: ... }`）。用 `context.Background()` 启动的循环停机时停不下来，等于白做优雅停机
- 任务日志清理循环：`log.retention_days` ≤0 显式关闭（启动 warn 一次）；>0 时每小时分批删（每批 5000，循环到不足一批，避免大事务锁表）

## 关键文件
- `cmd/recmaestro/main.go` —— `runScheduler` / `runWorker` 停机编排
- `internal/store/task_log.go` —— `TaskLogger.flushLoop`（ctx.Done flush）、`DeleteOlderThan`
- `internal/scheduler/log_cleanup.go` —— 清理循环与分批策略

## 为什么这么做（设计权衡 / 踩坑）
- 直接杀进程会把在写段截断成损坏段、丢掉未 flush 的任务日志（P-2 教训的延伸，见 TS 段合并防线）；scheduler 此前完全没有停机处理，与 worker 形成反差
- 日志按 `ts` 删除暂无单列索引（现有 `idx_task_ts` 以 task_id 打头，纯 ts 条件走全表扫描）——量大时再补 ts 索引，属已知取舍
- 停机顺序「先 Shutdown HTTP 再取消 ctx」：在途请求可能还在产生日志/投递，先关 HTTP 保证收口后 flush 的日志是完整的
