# 自动重试与心跳生命周期（max_retry / 心跳 zset 清扫）

## 是什么 / 规则

### max_retry 语义
- **只约束自动重试；手动重试（`POST /tasks/:id/retry`）不受限**——用户显式操作永远放行
- 自动重试有**两个守卫位置**，改任一路径时两处都要想到，漏一处就重新出现无限重试：
  1. worker `failAndRetry`：`FailWithRetry` 返回的新 retryCount ≥ `task.MaxRetry` → 不再 `queue.Schedule`，日志「自动重试次数已用尽」
  2. dispatcher `detectExpired`：recovering 长期未恢复置 interrupted 后，仅当 `task.RetryCount < task.MaxRetry` 才排自动重试
- **「不排期即终态」机制**：record_failed / interrupted 本身不区分"终态"与"可重试态"——没人再给它排 Schedule 它就是终态。`rebuildLoop` 只重建 queued 快照与 pending，不会捞 record_failed，所以"不再排期"就是安全的终态化
- retry_count 的计数来源：`FailWithRetry`（录制失败）与 `Retry`（手动）原子自增；**interrupted→自动重试→running 的中断循环不自增**。dispatcher 侧守卫读到的因此是"累计失败次数"而非中断轮数——够用但非严格语义，属已知取舍

### 心跳 zset 生命周期（防泄漏）
- 清扫**只在 scheduler `detectExpired` 一处收敛**，worker 侧不散加（多处清理容易漏改）
- 规则：`switch(task.Status)` 的 **default 分支（非 running/recovering）一律 `RemoveHeartbeat`**；`task==nil`（任务已删除）同样清残留
- **running/recovering 绝不能清**：recovering 靠心跳条目的 `LastAt` 判定 interrupt 时机（`hb.LastAt.Before(interruptCutoff)`）
- 清除无副作用：自动重试到点重新 running 后，`Heartbeat` 是 ZAdd 覆盖写

## 关键文件
- `internal/worker/worker.go` —— `failAndRetry()`（上限守卫）
- `internal/scheduler/dispatcher.go` —— `detectExpired()`（中断重试守卫 + default 清扫）
- `internal/store/task.go` —— `FailWithRetry` / `Retry`（条件 UPDATE + retry_count 自增）
- `internal/queue/queue.go` —— `Heartbeat` / `RemoveHeartbeat` / `ExpiredHeartbeats`

## 为什么这么做（设计权衡 / 踩坑）
- V0.1.0 之前 max_retry 建表默认 3 但**从未被读取**：断流任务理论上无限重试，一直占住调度与执行槽
- 心跳泄漏的慢性问题：终态任务条目永远留在 zset，每轮 recoverLoop 都对它空查一次 GetByID，条目随时间单调增长——不报错、只腐化，最容易漏
- 上限判断用 `FailWithRetry` 的**返回值**而非内存里的 `task.RetryCount`：认领时读到的值在执行期间可能过期，数据库自增后的返回值才是权威
