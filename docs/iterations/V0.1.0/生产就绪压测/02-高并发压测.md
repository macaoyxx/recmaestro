# 02 — 高并发压测

- 场景：高并发压测（API 吞吐 + 调度正确性）
- 日期：2026-10-15 11:13 ~ 11:35
- 环境：WSL Docker Compose 栈（scheduler + worker×3 + mysql + redis + consul + SRS 推流源），API/UI `http://127.0.0.1:8080`
- 压测工具：`docs/iterations/V0.1.0/生产就绪压测/scripts/loadgen/`（独立 go.mod，仅标准库，WSL 内 `go build` → `loadgen.bin`，go1.22.2）
- 开场核验：`ensure-stack.sh` 输出 healthz 200、worker×3、mysql/redis healthy；`ensure-stream.sh` 输出 SRS running、常驻推流 pid 323381、ffprobe 读流 OK（aac/h264）
- **总结论：不通过（2 个 P1 Issue）。** 稳态吞吐与调度正确性优秀（20 并发 10222 RPS 0 错误 p99=3.8ms；100 任务风暴认领唯一/无丢失/对账全过/全程无 5xx/worker 0 异常），但 ① 50/100 并发持续读压测出现 3.6%/10.4% 的 HTTP 500（scheduler→MySQL 连接风暴耗尽端口）；② 100 任务风暴超出 3×20=60 槽容量，40 个溢出任务终态 record_failed，断言「全部 completed」不成立。

## 目的

模拟大批量生产调用：①混合读压测（tasks/list、stats、audit-logs 权重混合）测吞吐与延迟分档；②登录限流验证 429 与恢复；③100 任务同时到期的任务风暴验证调度正确性（认领唯一/completed/对账/无 5xx）；④录制进行中 5 分钟混合耐力 + 30s 资源采样观察泄漏；⑤区分服务瓶颈与测试机瓶颈。

## 工具与口径

- `loadgen mixed`：闭环并发（每 goroutine 发完即发下一个），权重 tasks/list:stats:audit-logs = 5:3:2；错误 = HTTP≠200 或信封 code≠0；延迟为客户端全程。
- `loadgen loginburst`：串行连发**正确密码**登录（成功登录重置失败计数，不触发 5 次锁号，见 `internal/scheduler/handler_auth.go:16,55`）。
- `loadgen storm`：并发 10 创建任务，start/end 统一（RFC3339），同 SRS 源，录制内核默认 `-c copy` 转封装（`internal/recorder/recorder.go:134,272`），segment 30s。
- 采样：`scripts/tcpstat.sh`（scheduler netns TCP 状态/MySQL 指标/资源快照）、`scripts/endurance.sh`（30s 一轮 docker stats）。
- 断言 SQL：`scripts/storm_assert.sh`（mysql 客户端需 `--default-character-set=utf8mb4`，否则中文 LIKE 匹配 0 行——踩坑已记录）。

.../loadgen/loadgen.bin mixed -c <并发> -d 60 -token "$tok"

### 错误根因（Issue 高并发-1）

scheduler 日志（`docker logs recmaestro-scheduler --since 6m`，覆盖 100 并发档窗口）：

```
43577  ← grep -c 'cannot assign requested address'
43575  ← grep 'GIN' | grep ' 500 ' | wc -l
/app/internal/store/task.go:101  dial tcp 172.21.0.4:3306: connect: cannot assign requested address
[GIN] 2026/10/15 - 11:14:19 | 500 |  37.17ms | 172.21.0.1 | POST "/api/audit-logs/list"
```

根因链：`internal/store/db.go:23-24` 连接池 `max_open_conns=100 / max_idle_conns=20`（config/config.yaml:18-19），**未设 ConnMaxLifetime**。高并发波动下连接池反复收缩（回落只保 20 个 idle）再扩容新建，scheduler 容器 netns 内 TIME_WAIT 堆积耗尽 ephemeral port（`ip_local_port_range` 32768-60999），新建 MySQL 连接 `cannot assign requested address` → API 500。并发越高越恶性（RPS 反降：10222→6350→4743）。

对照证据（20 并发档压测中段，`scripts/tcpstat.sh`）：

```
== scheduler 容器 TCP 状态分布 (st: 01=ESTAB 06=TIME_WAIT) ==
    120 01        ← 0 个 TIME_WAIT，连接全复用
      1 0A
MySQL: Threads_connected=31  Max_used_connections=62（未触顶 100）
```

### p99 判断依据与瓶颈归属

- p99：20 并发 3.8ms / 50 并发 46.0ms / 100 并发 137.7ms。以「管理面 API p99<50ms」为达标线：20 并发档达标，100 并发档不达标；但 50/100 档的主导问题是 500 错误率而非纯延迟。
- **服务瓶颈，非测试机瓶颈**：16 核 WSL，loadgen 20 并发时仅 ~180% CPU；20 并发档打出全场景最高 RPS（10222）且 0 错误，证明负载发生端能力充足。服务端 scheduler ~450-500% CPU、mysql ~380-440% 亦未到 16 核上限，500 根因是连接管理（TIME_WAIT 耗尽）而非 CPU 饱和。

### Issue 高并发-2 定性

溢出任务行为链：60 槽先到先得（认领数 36/39/25 基本均衡）→ 第一批 11:32:11 停录合并完成后槽位释放 → 40 个排队任务此时认领，end_time 已过 → `worker.go:385` 录制循环直接 break → 0 段 → `worker.go:465` failAndRetry("未录制到任何段") → `worker.go:645` 判定已过期**不再重试**，终态 record_failed。每任务仍恰好 1 条 claimed（过期任务认领即终态，无重试再认领）。

直播语义下"错过开播即失败"合理，但**以 100 任务并发为生产需求衡量，当前 3 worker 配置容量不达标（60%）**，且溢出任务不排队/不顺延，直接终态失败。修复路径（用户决策）：扩 worker 副本（scale=5 即 100 槽）或上调 worker_capacity（需评估单节点 ffmpeg/IO 上限），或引入超量保护（提交时校验 scheduled_size 超容量告警）。
