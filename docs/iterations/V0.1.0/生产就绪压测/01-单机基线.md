# 01 — 单机基线

- 场景：单机基线（单 worker 全功能基线回归）
- 日期：2026-10-15
- 前置：00-环境预制 已完成（栈健康 + SRS 常驻推流）
- 结论：**核心功能全部验证通过，发现 2 个 P2 次要问题**（锁定后提示文案语义混淆、Redis 未设密码）。无 P0/P1。
- 测试数据（全部保留，未删除）：任务【单机基线-1】completed、【单机基线-2】record_failed（坏源终态）、【单机基线-3-已改名】cancelled；用户 baseline-lock-u1（user 角色，已解锁恢复 enabled）。

## 目的

单 worker（缩容至 1 实例）下跑全功能基线回归，确认系统出发点健康：
1. API 全链路冒烟（登录/限流/锁号/me/任务 CRUD/分页/统计/节点/审计/用户/失败信封）；
2. 一条真实录制端到端（SRS 源，时长对账 + ffprobe 复核 + 各下载接口）；
3. 坏源任务失败路径（自动重试上限、达终态后不再排期）;
4. SPA 资产抽查。

```
[   79s] FAIL 坏源留档 | http=404 size=72
```

复验（终态稳定后重新取详情、日志全文、容器目录、Redis 无认证直查）：

```
--- 任务终态详情 ---
status=record_failed retry_count=3 error_code=stream_unavailable
error_msg=源流不可用: exit status 1 (ffprobe: rtmp://127.0.0.1:1/no-such: Connection refused)
--- 任务日志全文 ---
10:53:25 [info][worker][claimed] worker 认领任务
10:53:25 [warn][worker][failed] 源流不可用: exit status 1 (ffprobe: rtmp://127.0.0.1:1/no-such: Connection refused)，10s 后自动重试（第 1 次）
10:53:38 [info][worker][claimed] worker 认领任务
10:53:38 [warn][worker][failed] …，10s 后自动重试（第 2 次）
10:53:53 [info][worker][claimed] worker 认领任务
10:53:53 [error][worker][failed] …，自动重试次数已用尽（3/3），终态失败
--- 容器内目录 ---
ls: /records/2110564321267290112/: No such file or directory
--- Redis 定时队列（无认证直查）---
ZRANGE recmaestro:scheduled 0 -1 WITHSCORES → （空）
ZCARD recmaestro:scheduled → 0
```

断言结论（全部成立）：
1. **自动重试有上限**：3 次认领失败（10:53:25 / :38 / :53，退避 10s 与 `config.go RetryBackoffFor` 前 3 次 10s 吻合），第 3 次 `retry_count=3` 达 `MaxRetry=3` 后终态 `record_failed`，日志『自动重试次数已用尽（3/3），终态失败』（`internal/worker/worker.go:663-668` 路径）。
2. **达终态后不再排期（不排期即终态）**：终态 75s 后（覆盖 2 个退避周期）状态与 retry_count 稳定不变；Redis `recmaestro:scheduled` ZCARD=0，队列中无该任务。
3. 失败原因来自 **ffprobe 预检防线**（`源流不可用: ffprobe … Connection refused`），未进 ffmpeg 录制阶段，故不创建录制目录、无 ffmpeg 留档 → 留档下载 404『日志文件不存在（任务可能尚未录制或合并）』，文案与行为一致，合理。
4. 复测脚本一处假证据修正：首轮 Redis 断言因向无密码 Redis 发送 AUTH 报错（`ERR AUTH … called without any password configured`）而 ZRANGE 实际未执行；复验以无认证直查为准（见 Issue 单机基线-2）。

**状态语义观察（设计现状，非缺陷）**：`record_failed` 同时用于「重试等待中」与「终态失败」两种处境（`failAndRetry` 先置 record_failed 再排期唤醒），仅凭 status 无法区分是否还会自动重试，需结合 retry_count/任务日志。前端详情页有 retry_count 可见，暂不影响使用，记录备查。
