## 结论与观察项

1. 三层防线实测有效：①优雅停机在 SIGTERM 下完整收尾（本例 0.5s 退出让 ffmpeg 封完当前段）；②段预检隔离机制在位（5 个任务的合并日志均为"隔离损坏 0 段"——TS 前缀截断可解码的近无损特性与 memory 记录一致，预检防的是头部/同步字节损坏的小概率）；③时长对账全部通过且 ffprobe 复核一致（6/6 任务：145.6/356.0/536.2/304.5/185.6s + 场景 2 的 ffprobe 355.96s）。
2. 宕机恢复链路稳定：停机→recovering 实测 4m01s~4m12s（recover_window 3m + tick 对齐，符合口径）；原节点 start 后 5~6s 接管续录（SLA 15s 内）；start_seq 每次与磁盘/DB 段号正确衔接（4、2、5）。
3. 重试约束符合设计：自动重试显式排期（"10s 后自动重试（第 N 次）"），retry_count 落库（2/3），用尽前恢复即续录成功；人工重试入口独立（未触发）。
4. scheduler 单点行为如实：强杀期间 8080 拒连（healthz=000、list=FAIL），但 worker 录制零损失、恢复 4s 内 200、队列按 MySQL 重建且无重复派发。
5. MySQL 短暂重启（~5-15s）影响面极小：仅 1 个采样周期 list 失败，失败路径标准 500 信封；恢复后写入立即自愈。

### 观察项（非断言失败）

- **[P2] worker 的 /healthz 受内部接口鉴权保护，匿名探测返回 401**（场景 3 附带发现：`curl worker:8080/healthz` → 401；scheduler 的 /healthz 为 200）。worker healthz 挂在 InternalRouter（cmd/recmaestro/main.go:173）内随共享密钥中间件一起被保护。节点判活走 Redis 心跳租约（架构铁律 3）不受影响，但外部监控若用匿名 healthz 探测 worker 会误判不健康。是否放行匿名 healthz 由维护者裁决。
- 部署形态备注：worker×3 共享 named volume `worker_records`（deploy/docker-compose.yml:98），单机形态下文件视图互通——不影响"任务绑定节点+经 worker 内部接口操作文件"的架构约束，仅作记录。
- 测试工具坑（供后续场景复用，均已规避）：①WSL 会话退出会清理 nohup 后台采样器，采样必须与主流程同一条 wsl 命令（或会话内 wait）；②任务日志 API 按时间倒序返回，"完成/对账"行在 head 不在 tail；③worker 容器 stdout 无"认领"行（认领日志只在任务日志表），认领次数用 `stage=claimed` 统计。
