# 03 — 集群与动态扩展

- 场景：集群扩展（动态扩缩容与任务绑定规则）
- 日期：2026-10-15 11:42 ~ 12:07（WSL Docker 栈）
- 结论：**功能断言全部通过**；登记 1 条「疑似」Issue（批量建任务过程中偶发一次登录无响应→401，重试成功，根因未定），按纪律 pass=false
- 测试数据：全部保留（任务名【集群扩展-*】共 18 条，含 1 条命名失误后取消的记录）

## 一、目的

验证 RecMaestro 在运行中动态扩缩容的行为与架构铁律「任务绑定节点、宕机等原节点、不跨节点迁移」：

1. 运行中扩容 1→3→5，新节点 30s 内注册，新任务被新节点认领；
2. 抽 3 个运行中任务，扩容/缩容/恢复全程 worker_id 不变；
3. 停录制中任务所在 worker：转 recovering（约 3 分钟 recover_window）、其他 worker 不抢、原节点恢复 15s 内续录、完成后对账通过；
4. 实测心跳下线判定时延与重新上线时延；
5. 5 实例并发 10+ 任务无异常，终态恢复 3 实例。

## 二、环境与前置

- 开场第一步按纪律执行：`ensure-stack.sh`（healthz 200、worker×3、mysql/redis healthy）+ `ensure-stream.sh`（SRS 推流 ffprobe 读流 OK）+ WSL 保活（`pgrep -f 'sleep infinity'` → pid 587 在跑）。
- 基线快照（`cluster-peek.sh`）：3 节点全空闲（current_tasks=0），无运行中任务；历史遗留【压测-*】任务 104 条（上一场景数据，按纪律不动）。
- 本场景脚本（均在本目录 `scripts/`，WSL 内 bash 调用）：
  `cluster-peek.sh`（节点+任务快照）、`cluster-wait-nodes.sh`（轮询节点总数）、`cluster-create.sh`（建任务，end_time=now+N 秒）、`cluster-task.sh`（任务状态）、`cluster-ip2worker.sh`（容器↔IP 映射）、`cluster-poll-task.sh`（轮询任务状态）、`cluster-poll-node.sh`（轮询节点出现/消失）、`cluster-task-log.sh`（关键日志过滤）、`cluster-concurrency.sh`/`cluster-wait-all.sh`（并发批量+终态等待）、`cluster-final.sh`（终态恢复核验）。
- 机制代码事实（报告断言的依据）：
  - worker 认领 = Redis BLPop 竞争出队 + 容量检查，**无 least-loaded 指派**（`internal/worker/worker.go:259-308`）；
  - 节点下线判定 = scheduler `nodeSyncLoop` 每 30s tick，心跳租约超时即**从节点表删除**（`internal/scheduler/metrics_collector.go:51-84`），重新上线由 worker 心跳 Upsert 再注册；
  - `recover_window: 3m`（`config/config.yaml:60`），worker 心跳超时进 recovering。

## 五、Issue 与观察

### Issue 集群扩展-1（P2，疑似）：批量建任务中第 9 次登录瞬时无响应，导致该次创建 401

- 现象：`cluster-concurrency.sh` 连续创建 10 任务，第 9 个返回 `HTTP 401 {"msg":"未提供认证信息"}`（前 8 个 201 正常）；脚本内 `login.sh` 本次输出空 token（其 `curl --max-time 10` 调 `/api/login` 未取得含 access_token 的响应，login.sh 静默 exit 1，stderr 未被透传）。
- 处置：单独验证 login 正常（token_len=249、stats 200），补建【集群扩展-并发-9/10】成功，无任务丢失。
- 定性：**疑似**——当时 10 任务并发起录、scheduler 负载抬升，无法排除 `/api/login` 瞬时超时/出错；亦可能是 WSL 侧网络抖动。未复现、无服务端日志佐证，根因未定。影响面小（客户端重试即恢复），定 P2。

### 观察（不构成缺陷）

1. **认领非 least-loaded**：扩到 5 后任务 4 落到已有负载的 0.8 而空闲 worker-4 未得；并发阶段分布 4/3/2/1/0。机制为 Redis BLPop 竞争出队（worker.go:268-296），无按负载指派；capacity=20 内不构成风险，如需均匀需产品层引入指派策略（超出本场景范围）。
2. 节点表语义：下线即移除（非置 offline 字段），页面/API 以「消失/重现」表达节点离线（metrics_collector.go:79-81 注释为有意设计）。
3. 收敛时延参考：compose 移除容器 → 节点表移除 27~50s（心跳 TTL+30s tick）；重建/恢复 → 注册 1~2s。

## 复测四、与原场景差异点说明（均为机制内，不构成缺陷）

1. **转 recovering 278s（原 186s）**：机制为 `recoverLoop` ticker = `recover_window/2` = 90s（`internal/scheduler/dispatcher.go:162`），每轮 `detectExpired` 以 `cutoff=now-180s` 判心跳超时（dispatcher.go:186-208）。时延 = 180s 窗口 + 0~90s tick 对齐 + 最后一次心跳距 stop 的偏移 + 5s 轮询观察粒度，上界约 305s；186s 与 278s 均在此设计区间，属 tick 相位差，非回归。口径「约 3 分钟 recover_window + tick 对齐」成立。
2. **受试产物 63.4s 远小于 360s 窗口**：停机空窗 ~310s（stop 14:34:47 → 续录 14:39:57）为设计内损失，有效录制 ≈ 认领~stop 25s + 续录~end 24s + 段边界；验收口径=时长对账（63.4s=段合计 63.4s）非窗口时长，通过。
3. **并发分布 2/2/2/2/2 恰好均衡（原 4/3/2/1/0）**：BLPop 竞争消费的分布本不保证均匀（原场景已登记为观察项），本轮恰好均衡属随机结果，无机制变化。
