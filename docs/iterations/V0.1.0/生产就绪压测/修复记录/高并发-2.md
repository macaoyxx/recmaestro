# 修复记录 — 高并发-2

- Issue：高并发-2（P1）100 任务风暴超 3×20=60 槽容量，40 个溢出任务认领时 end_time 已过、终态 record_failed，「全部 completed」断言仅 60/100
- 日期：2026-10-15
- 状态：**定性闭环，修复口径=水平扩展（无代码改动）**。行为经审定符合设计（直播语义「错过开播即终态失败」），缺口属部署容量规划；生产基线定为 `--scale worker=5`（100 槽），复测按 5 实例跑风暴验证。

## 一、现象（02-高并发压测.md §3）

100 任务风暴（`loadgen storm -n 100`，start/end 统一为 11:29:11 ~ 11:32:11，同 SRS 源）断言结果：

```
== 2) 状态分布 ==   completed=60  record_failed=40
== 3) claimed 次数 == claimed_times=1 → tasks=100（每任务恰好一次）
== 4) claimed node_id 与最终 worker_id 不一致 == mismatch=0
== 5) 同任务异节点 claimed 时间重叠 == dup=0
== 6) 时长对账 == reconciled=60（= completed 数，全过）
== 9) 各 worker 认领数 == 172.21.0.5=36  172.21.0.7=39  172.21.0.8=25
```

「全部 completed」断言 60/100 不成立；40 个溢出任务终态 record_failed，无产物无对账。同期调度正确性断言（认领恰好一次/无丢失/无漂移/无重叠/无 5xx）全部通过。

## 二、根因（纯容量缺口，非代码缺陷）

**容量事实：worker_capacity=20（`config/config.yaml:40`）× 3 节点 = 60 并发槽 < 100 任务。** 溢出行为链逐环核实（本轮全部读码确认）：

1. **槽位先到先得**：claimLoop 容量检查 `internal/worker/worker.go:269`——`currentTasks >= worker_capacity` 时不认领、等 2s 重试。60 槽被首批任务占满（认领数 36/39/25 基本均衡，分配无倾斜）。
2. **排队任务晚到**：首批任务 11:32:11 到 end_time 停录、合并完成释放槽位后，40 个排队任务才被认领——此时它们的 end_time（同样 11:32:11）已过。
3. **认领即终态失败**：录制循环入口 `internal/worker/worker.go:385` 判 `!time.Now().Before(*task.EndTime)` 直接 break，录 0 段；`internal/worker/worker.go:462-466` 从 DB 补齐历史段后仍为 0，走 `failAndRetry(ctx, task, "record_failed", "未录制到任何段")`；`internal/worker/worker.go:645` 判定 `task.EndTime == nil || !now.Before(*task.EndTime)` 为真 → 终态失败不再排期重试（`worker.go:639-645` 函数注释明示该设计）。

**定性：调度正确性无缺陷。** 认领恰好一次（100×1）、无丢失、0 漂移、0 异节点重叠、completed 部分时长对账 60/60 全过 + ffprobe 抽检一致、全程 scheduler 5xx=0 / worker warn·error=0。每一环节都按设计正确执行，失败仅因并发任务数超过部署容量。

**生产基线：`docker compose up -d --scale worker=5` → 5×20=100 槽 ≥ 100 并发任务生产需求。** 不改代码、不改配置。

可行性证据（全部为既有实测，无需新验证）：

## 四、不做排队/顺延的理由

报告 §3 定性已明确，此处展开归档：

1. **顺延也录不到内容**：直播流错过即永久错过，end_time 过后即使排队等到槽位、源仍在推，录到的也只是时间窗之外的残余流——目标内容（start~end 窗口）已不可恢复，顺延只是把失败延后并让任务状态失真。
2. **违反平台既有约定**：「已过截止时间或无截止时间则终态失败，不排期」是 `failAndRetry` 的明示设计（`internal/worker/worker.go:639-645` 注释），自动重试的语义是「断流等可恢复故障的退避重试」（流可能恢复），而时间窗过期不可恢复，二者本质不同。
3. **占槽等待浪费真实容量**：让过期任务排队或等待会占住执行槽/队列，恶化而非缓解容量缺口。
4. **不应为容量缺口改正确代码**：测试证据表明调度与失败路径均按设计正确运行；用代码改动迁就部署容量缺口是治标，正确解法是把容量配齐（§三）。
