# 修复记录 — 单机基线-1

- 问题：连续密码错误锁定后再次登录提示『账号已被禁用』而非『账号已锁定』，锁定与禁用两种成因对用户不可区分（P2）
- 场景：单机基线（api-smoke.sh `[1s] FAIL 锁定后登录 | http=403 code=403 msg=账号已被禁用`）
- 日期：2026-10-15
- 状态：已修复，定向复现转绿（单测层）；栈上复测待新镜像部署后由复测代理执行

## 现象（WSL Docker 栈上定向复现）

复现脚本（WSL 内执行，admin 密码经 login.sh 读取未回显）：创建用户 `fix-lock-u1`（user 角色）→ 连续 5 次错密码 → 正确密码登录。

```
第 1~4 次错密码：{"code":401,"data":null,"msg":"用户名或密码错误"} http=401
第 5 次错密码：  {"code":403,"data":null,"msg":"密码错误次数过多，账号已锁定"} http=403
锁定后正确密码登录（复现点）：
               {"code":403,"data":null,"msg":"账号已被禁用"} http=403
               ← 预期「账号已锁定，请联系管理员」（handler_auth.go 原 :55-59 分支）
```

拒绝行为本身正确（403），但文案成因混淆。收尾已将 fix-lock-u1 enable 解锁恢复 enabled（测试数据保留未删）。

## 根因

锁定机制的实现复用了 `disabled` 状态：第 5 次错密码时账号被置 `StatusDisabled`（`internal/scheduler/handler_auth.go` 锁定路径的 `UpdateStatus` 调用）。登录处理中 `u.Status == store.StatusDisabled` 检查排在 `u.FailedLoginCount >= maxFailedLoginAttempts` 检查之前，导致锁定用户（disabled + 计数≥5）恒走禁用分支返回「账号已被禁用」，锁定计数分支成为不可达代码。

判别依据（为什么调换顺序是安全的）：`IncrFailedLogin` 只在账号 enabled 时可达（disabled/锁定检查均先于密码校验返回），失败计数达 5 的瞬间账号即被置 disabled，因此「disabled + 计数≥5」⟺ 登录锁定成因，「disabled + 计数<5」⟺ 管理员禁用成因。enable（`handler_user.go` 的 `Unlock` 调用，清零计数）与重置密码两条恢复路径不受影响。

## 修复

`internal/scheduler/handler_auth.go` handleLogin：将失败计数（锁定）检查移到禁用检查之前，并加中文注释说明成因区分依据。仅调换两个检查块的顺序，无其他逻辑变更：

- 锁定成因（disabled + 计数≥5）→ 403「账号已锁定，请联系管理员」（含 AuditLoginLocked 审计）
- 管理员禁用成因（disabled + 计数<5）→ 403「账号已被禁用」
