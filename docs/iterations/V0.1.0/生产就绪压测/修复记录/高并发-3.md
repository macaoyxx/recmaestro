## 一、现象（02-高并发压测.md「补录复测 R2」节）

- 100 路于 16:27:46 统一停录，收尾洪峰打满 MySQL：`Max_used_connections=152`、`Connection_errors_max_connections=153`，deploy-worker-6 日志 `internal/store/task.go:76 Error 1040: Too many connections`（16:28:07/08）。
- 【压测R-78】(2110647684950921223)、【压测R-42】(2110647685064167424)（均归属 worker-4/172.21.0.8）：主表 running（updated_at 停在 16:28:08/09）、文件表无 output.mp4 记录（磁盘产物在）、日志表 16:28:11 已有 validated/completed——三表永久不一致。
- 16:38:09 复查仍 running（超 recover_window 3 倍无自愈）。

## 二、根因（两层，缺一不可）

### 1. 部署侧：MySQL max_connections=151 与「scheduler 大池 + 5 worker」拓扑不匹配

高并发-1 修复将连接池改为 `max_idle_conns=100`（峰值连接全量持有 10m），但该配置为 scheduler/worker 共用的 `config/config.yaml` 公共默认。总账演变：

- 修复前（3 worker 低负载）：Threads_connected 37~74，不触发；
- 修复后（5 worker）：理论上限 = scheduler 100 + 5×worker 100 = **600 ≫ 151**。停录洪峰（100 路同时收尾写库 + scheduler 持有 R1 压测残留 idle 连接）实际打到 152（151+1 admin 保留位），worker 收尾链撞 Error 1040。

### 2. 代码侧：收尾链路 `_ =` 吞错把瞬时拒绝放大为永久数据损伤

`internal/worker/worker.go`（修复前 612/623 行）收尾链：

```go
_ = w.files.Create(...)    // 产物记录：失败被吞 → 文件表永久缺记录
...cleanupSegments...      // （顺序问题：段清理在 Complete 之前，失败时现场已销毁）
_ = w.tasks.Complete(...)  // 终态：失败被吞 → 主表永久 running
_ = w.queue.RemoveHeartbeat(...)  // Redis 不受 1040 影响，成功删除
w.logger.Log(completed)    // 异步批量写，稍后成功 → 日志表 completed
```

`store/task.go` Complete 为单条 UPDATE 无重试。更致命的是**无自愈路径**：心跳已被 RemoveHeartbeat 删除 → scheduler `detectExpired`（dispatcher.go:187 `ExpiredHeartbeats`）查不到该任务 → 永不置 recovering → worker 的 resumeLoop 也只认 recovering → 节点活着但任务永久 running。任何一环（重试/不删心跳/自愈扫描）存在都不至于永久卡死，当时全部缺失。

## 三、修复内容

### 代码（worker 收尾链 + 自愈循环）

| 改动 | 位置 | 说明 |
|---|---|---|
| 收尾写库有界重试、绝不吞错 | `worker.go` finishTask + 新增 `finalizeDBOp` | 产物记录与终态两步各经 `finalizeDBOp`：4 次尝试、退避 1s/2s/4s（跨瞬态抖动）；每次失败 `[error]` 响亮报出（项目首个 `[error]` 前缀，可 grep）；穷尽仍失败走 `reportFinalizeFailure`：stdout ERROR + 任务日志表 error 双通道、保留 TS 段与产物现场 |
| 收尾顺序调整：终态先于清段 | finishTask | cleanupSegments 从 Complete 之前挪到之后——MySQL 是真相源，终态对用户可见后才销毁段现场；终态写库失败提前 return 保留段。**防线不破坏：清理仍严格在时长对账通过之后**（.memory 三层防线口径） |
| 幂等自愈循环 healLoop | `worker.go` 新增 healLoop/healFinalizePending/healTask（15s 周期，与 resumeLoop 一致） | 扫描本节点名下 running 且不在 in-flight 集合的任务，判定铁证 = **日志表有 validated 记录**（时长对账通过的持久化证据，防线③的落库痕迹）+ 磁盘 output.mp4 存在且 ffprobe 可探测 → 幂等补写产物记录 + 终态 + completed 日志。worker 重启后同样接管（Run 启动即跑） |
| in-flight 集合防竞态 | Worker.inflight (sync.Map)；claimLoop/resumeOwnTasks 在改状态**之前** Store 占坑 | 保证 healLoop 快照命中任务时必能查到占坑，杜绝「Claim 提交与执行登记之间把重试任务误补 completed」及 resume 同类竞态；A/B 撞击分析见代码注释 |
| Complete 拆无条件/条件两版 | `store/task.go` 新增 `CompleteRunning`（仅 running→completed） | 收尾与自愈用条件版：防止自愈把人工中止/取消等并发处置覆盖回 completed；手动合并路径（internal_api.go merge_failed→completed）保留无条件版语义不变 |
| 产物记录幂等创建 | `store/task_file.go` 新增 `CreateOutputIfAbsent` | 重试时上次可能已实际写入（连接断在 commit 后），不能产生重复行（表无唯一索引，应用层 FirstOrCreate） |
| 自愈判定查询 | `store/task.go` 新增 `ListRunningByWorker`、`store/task_log.go` 新增 `HasStage` | |

**取舍说明**：
- 自愈判定不用「重跑时长对账」而用「validated 日志铁证」：事故任务的 TS 段已被清理（旧顺序 cleanup 在 Complete 前），重对账无数据可对；validated 日志只在防线③通过后写入，是「内容已验收」的直接证据。代价是极端场景（validated 日志也丢了）不自动补，保持 running 人工介入——宁可保守不误标。
- 重试 4×(1s/2s/4s) 不追求扛过 3 分钟打满期：打满期交给 healLoop（DB 恢复后 ≤15s 收敛），收尾 goroutine 不长时间占执行槽。
- `reportFinalizeFailure` 删除 Redis 心跳：录制确实已结束，不删会被 recoverLoop 误判心跳超时置 recovering 走重录路径（重录会把已完成任务误标 record_failed）。

### 部署（连接池按角色分化 + max_connections 容量算式）

| 改动 | 位置 |
|---|---|
| 新增 `MYSQL_MAX_OPEN_CONNS`/`MYSQL_MAX_IDLE_CONNS` 环境变量覆盖 | `internal/config/config.go` applyEnvOverrides |
| worker 服务注入池上限 30/30 | `deploy/docker-compose.yml` worker.environment |
| MySQL `--max_connections=300` | `deploy/docker-compose.yml` mysql.command |

**容量算式**（已写入 compose 注释）：

```
max_connections(300) = scheduler 池上限 100          （高并发 API 面，高并发-1 修复口径，不动）
                     + worker 5 副本 × 池上限 30 = 150（worker_capacity=20 槽执行器：
                                                   DB 并发 ≈ 20 路收尾/段上报 + 后台循环，
                                                   池 30 = 观测峰值 ~10/节点 的 3 倍）
                     + 运维/监控余量 50
扩容指引：每 +1 worker 副本 +30，同步上调 max_connections。
```

实测依据：压测观察 5 节点停录洪峰 worker 侧连接合计 ≈ 50（≈10/节点）；修复后部署实测每 worker 常态 3~4 连接、Threads_connected=22，总账上限 300 有充分余量。
