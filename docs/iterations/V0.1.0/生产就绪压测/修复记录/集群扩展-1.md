# 修复记录 — 集群扩展-1

- Issue：集群扩展-1（P2，疑似）批量建任务中第 9 次登录瞬时无响应导致该次创建 401（重试即恢复，根因未定）
- 日期：2026-10-15
- 状态：**已修复并复现验证通过**（根因已定，非瞬时无响应/网络抖动）

## 一、现象（原文报告 §3.7 / §五）

`cluster-concurrency.sh 10 180` 连建 10 任务，前 8 个 HTTP 201，第 9 个 `HTTP 401 {"msg":"未提供认证信息"}`；脚本内 `login.sh` 本次输出空 token。随后单独验证 login 正常（token_len=249），补建成功。原报告因未复现、无服务端日志佐证（当时 scheduler 容器后续已被 05 灾备场景重建，历史日志丢失）标「疑似、根因未定」。

## 二、根因（已实锤复现）

**登录限流 429 被客户端脚本转成空 token，再以无 Authorization 头打创建接口，形成误导性 401。** 与「瞬时无响应」「WSL 网络抖动」「scheduler 负载」均无关。

失败链（每一步都在当前栈上定向复现）：

1. `/api/login` 挂了 IP 限流：每 IP 每分钟 10 次，超限 `429 {"msg":"登录尝试过于频繁，请稍后再试"}`（`internal/scheduler/server.go:100`、`internal/scheduler/login_ratelimit.go:18` 固定窗口 `loginRateLimit=10`）。所有脚本调用经 docker 网关，ClientIP 恒为 `172.21.0.1`，共用同一限流桶。
2. `cluster-concurrency.sh` 循环逐个调 `cluster-create.sh`，后者**每次建任务前都重新登录**（原 `cluster-create.sh:12`），批量用法必然打爆配额。
3. 时序精确吻合：§3.6 心跳时延测试中 vanish/appear 两次 `cluster-poll-node.sh` 各登录 1 次（12:00:52 / 12:01:05，同窗口 count=2）→ 并发第 1~8 轮各登录 1 次恰好用满 10 次配额 → **第 9 轮 429**（`allow()` 对被拒请求也计数，`login_ratelimit.go:48-49`）。
4. `login.sh` 对 429 响应提取不到 `access_token` → stdout 空、exit 1（诊断信息打在 stderr，被 `cluster-create.sh` 的 `capture_output` 吞掉，故当时看不到 429 字样，误判「无响应」）。
5. `cluster-create.sh` 拿空 token 继续发 `POST /api/tasks` → 无 Authorization 头 → `internal/auth/middleware.go:24` 返回 `401 {"msg":"未提供认证信息"}` —— 正是报告记录的第 9 个任务的响应。
6. 「稍后手工验证正常」也自洽：429 后约几十秒固定窗口滚动重置，下一次登录即放行。

## 三、修复（最小改动，只动测试脚本，服务端不动）

服务端限流是设计内安全特性（`login_ratelimit.go:1-3` 注释「遏制撞库与暴力破解」），不为压测用法放宽；缺陷在脚本用法与错误透传：

| 文件 | 改动 |
|---|---|
| `scripts/cluster-concurrency.sh` | 循环前登录一次并 `export RM_TOKEN` 整批复用（批量 10 任务登录次数从 10 → 1）；`KEYWORD` 支持环境变量覆盖（默认值不变，bash 与尾部统计 python 两处同步），便于验证数据与场景数据区分 |
| `scripts/cluster-create.sh` | 支持 `RM_TOKEN` 复用（有则不再登录）；需登录而失败时**立即终止并透传 login.sh 的 stderr**（`sys.exit(2)`，不再拿空 token 打创建接口造成误导性 401） |

## 四、验证（均在 WSL Docker 栈上定向执行，2026-10-15 14:0x~14:12）

1. **根因复现**：同 IP 连续 12 次 `POST /api/login`（密码不回显）→ 前 3 次 200（当前窗口已有 7 次 hit），**第 4 次起全部 429**，body `{"code":429,"msg":"登录尝试过于频繁，请稍后再试"}`。
2. **失败链复现**：无 Authorization 头 `POST /api/tasks` → `{"code":401,"msg":"未提供认证信息"} http=401`；窗口满时跑 `login.sh` → exit=1、token_len=0、stderr 显示 429 body——完整还原当时现象。
3. **修复后转绿（原始规模）**：`KEYWORD=集群扩展-修复验证 bash cluster-concurrency.sh 10 30` → **10/10 全部 HTTP 201，无一 401**，10/10 被认领 running（3 节点分布 4/2/4），统计 keyword 区分生效。
4. **服务端日志佐证**：`docker logs recmaestro-scheduler` 显示该批量期间 `/api/login` 仅 2 次（14:12:01 批量前 1 次 + 14:12:23 统计段 1 次，均 200）——复用生效，远低于 10 次/分钟阈值。

未验证项：`cluster-create.sh` 的 fail fast 分支（需登录失败才触发）未单独注入复现，逻辑为发请求前 `sys.exit(2)`，由上述第 2 步的 login.sh 失败行为 + 代码审读共同支撑。
