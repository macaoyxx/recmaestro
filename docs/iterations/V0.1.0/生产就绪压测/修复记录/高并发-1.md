# 修复记录 — 高并发-1：50/100 并发持续读压测 API 间歇 500，连接池 churn 致 ephemeral port 耗尽

- 问题编号：高并发-1（P1）
- 日期：2026-10-15
- 关联证据：`02-高并发压测.md` §1（混合读压测 50/100 档错误率 3.63%/10.44%，全部 HTTP 500）

## 现象

50/100 并发 60s 混合读压测（tasks/list:stats:audit-logs = 5:3:2）阶段爆发 HTTP 500：100 并发档 29743 错（10.441%），scheduler 日志 `cannot assign requested address` 43577 条（`internal/store/task.go:101 dial tcp 172.21.0.4:3306`），并发越高越恶性（RPS 10222→6350→4743 反降）。对照 20 并发档 0 错误、TIME_WAIT=0 连接全复用。

## 根因

`internal/store/db.go:23-24` 只设了 `SetMaxOpenConns(100)` / `SetMaxIdleConns(20)`，连接池无生命周期治理：

1. **churn 直接根源是 idle 池（20）远小于峰值打开数（观测 MySQL Max_used=62）**：`database/sql` 归还连接时超出 `MaxIdleConns` 的立即关闭。高并发波动下池反复"回落关闭 → 再高峰重建"，每次关闭由客户端主动发 FIN，连接的 ephemeral port 在 scheduler 容器 netns 进 TIME_WAIT（存活 60s）。
2. 未设 `ConnMaxLifetime`/`ConnMaxIdleTime` 只是问题的一半——**仅补这两个参数不能消除 churn**（idle 池小依旧每次回落关连接），真正的治理是让峰值连接全量复用 + 长寿命/空闲连接的定期轮换。
3. 60s 窗口内积累数万 TIME_WAIT → `ip_local_port_range`（32768-60999，约 28k 个）耗尽 → 新建 MySQL 连接 `cannot assign requested address` → API 500。

## 修复（连接复用治理三件套）

最小改动，全部走既有配置链路（池参数一直放 config.yaml，跟随现有风格；scheduler 与 worker 共用 `NewDB`/同一配置）：

| 文件 | 改动 |
|---|---|
| `internal/store/db.go` | 补 `SetConnMaxLifetime` / `SetConnMaxIdleTime`（0 值 = 不限制，database/sql 语义），附连接复用说明注释 |
| `internal/config/config.go` | `MySQLConfig` 增加 `ConnMaxLifetime` / `ConnMaxIdleTime`（`time.Duration`，viper 自带 StringToTimeDuration 解析，同 `retry_backoff`/`jwt.expire` 先例） |
| `config/config.yaml` | `max_idle_conns: 20 → 100`（与 `max_open_conns` 等大，峰值连接全量保留复用，消除收缩扩容 churn）；新增 `conn_max_lifetime: 1h`（轮换长寿命连接，规避 MySQL `wait_timeout` 断连产生的陈旧连接，轮换速率 ≈ 每连接每小时 1 次，无堆积风险）、`conn_max_idle_time: 10m`（低负载时释放空闲连接） |

**MySQL 总账核算**（max_connections 默认 151，scheduler 与 worker×3 共用）：`max_open_conns=100` 不动（保吞吐上限）；idle=open 后稳态连接 ≈ scheduler 峰值 ~100 + worker×3 个位数 + root 会话。修复后实测 `Max_used_connections=108 / 151` 未触顶；压测停止 10 分钟后 `conn_max_idle_time` 自动收缩回低水位。若后续扩 worker 副本（高并发-2 方向 scale=5）导致总账逼近 151，需在 deploy compose 的 MySQL command 加 `--max-connections` 上调，单侧再调大池无意义。

## 验证（WSL Docker 栈，2026-10-15 下午，口径与 02 场景一致）

1. 静态：`go build ./...` + `go vet ./internal/store/ ./internal/config/` 通过；临时程序加载 `--env=local` 配置确认解析为 `open=100 idle=100 lifetime=1h idle_time=10m`（验证后已删）。
2. 部署：`docker compose up -d --build` 重建 + `--scale worker=3` 还原 3 节点口径（healthz 200）。
3. **100 并发 60s 混合读（ask 指定断言）：错误 0/414330（0.000%）**，RPS 6904.6（修复前 4743.2，+46%），p99=38.9ms（前 137.7ms），max=128.3ms。
4. 压测中段采样：scheduler netns **TIME_WAIT=0**（136 ESTAB 全复用）；MySQL `Threads_connected=105`、`Threads_running=4`。
5. 50 并发 60s：错误 0/393143，RPS 6551.4（前 6350.6），p99=18.8ms（前 46.0ms）。
6. 20 并发 60s（回归对照，连跑、冷却 90s、空闲收缩后各一轮）：错误 0，p99=8.0/8.5/8.5ms。RPS ≈5428~5549，低于 02 场景的 10222——**服务端无回退证据**：① scheduler GIN 日志 tasks/list 服务端延迟集中 1.75~2.08ms，与 10222 那轮（客户端 p50=1.8ms ≈ 服务端全程）同量级，差额 ~1.5ms 在客户端/环境侧（全场景 01-06 跑完 + 本日连续四轮压测后的机器余热）；② 定向排除实验：压测停止 10 分钟待 `conn_max_idle_time` 生效、MySQL `Threads_connected` 从 109 收缩到 14 后复测，RPS 5534.3 与高连接水位时（5549）一致——RPS 差异与连接池参数无关（该实验同时验证了空闲收缩机制真实生效）。断言项（错误率 0、p99 达标）均满足。
7. 修复后容器全程日志：`cannot assign requested address` 0 条、GIN 500 计数 0。
8. 全量单测未跑（按分工留给脚本门禁）。
