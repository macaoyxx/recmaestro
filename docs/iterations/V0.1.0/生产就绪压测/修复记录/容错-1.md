# 修复记录 — 容错-1：worker /healthz 被内部接口鉴权保护，匿名探测 401

- 问题编号：容错-1（P2）
- 日期：2026-10-15
- 关联证据：`04-容错与异常恢复.md`「观察项」节（场景 3 附带发现）

## 现象

场景 3 注入后 `curl http://127.0.0.1:<worker映射端口>/healthz` → 401（HTTP 服务正常响应、进程存活）；同刻 scheduler 的 `/healthz` 为 200。外部监控若用匿名 healthz 探测 worker，会把健康节点误判为不健康。节点判活走 Redis 心跳租约（架构铁律 3）不受影响。

本次修复前在 WSL Docker 栈复现（2026-10-15 14:0x）：

```text
$ wsl docker ps：deploy-worker-3 -> 8082、deploy-worker-1 -> 8083、deploy-worker-2 -> 8084、scheduler -> 8080
worker(127.0.0.1:8082)/healthz -> 401
worker(127.0.0.1:8083)/healthz -> 401
worker(127.0.0.1:8084)/healthz -> 401
scheduler(127.0.0.1:8080)/healthz -> 200
worker(8082)/metrics -> 401          ← /metrics 同样被拦截（Prometheus 抓取也会失败）
```

## 根因

- `internal/worker/internal_api.go:23`（修复前）：`InternalRouter()` 把共享密钥中间件挂在 **engine 级** `r.Use(gin.Recovery(), w.internalAuth())`，对该 engine 上所有路由生效。
- `cmd/recmaestro/main.go:172-174`：worker 角色把 `/healthz`、`/metrics` 注册在 `InternalRouter()` 返回的同一 engine 上 → 被鉴权拦截，匿名返回 401。
- 对照 scheduler 侧：`internal/scheduler/server.go:97-104` 鉴权只挂 `/api` 分组，顶层 `/healthz`、`/metrics`（main.go:119-120）匿名可访问，故 scheduler 200。

## 修复

最小改动：鉴权从 engine 级收敛到 `/internal` 分组（与 scheduler「鉴权挂分组」风格一致），`/healthz`、`/metrics` 恢复匿名；`/internal/**` 的鉴权语义、路由路径均不变（scheduler→worker 的内部调用不受影响）。

- `internal/worker/internal_api.go`：`InternalRouter()` 改为 `r.Group("/internal", w.internalAuth())` 挂载四条内部路由；同步更新包注释。
- `cmd/recmaestro/main.go`：无需改动（/healthz、/metrics 注册位置不变）。

附带收益：`/metrics` 同步恢复匿名，外部 Prometheus 可直接抓取 worker 指标。
